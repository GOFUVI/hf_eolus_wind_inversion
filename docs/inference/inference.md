# HF‑Radar Wind Inference

## Overview
This document describes how model inference is performed from coastal HF‑radar data using the artifacts generated by the training pipeline. The inference entry point (`scripts/inference/inference.py`) loads the trained network weights, the embedded normalization parameters, and the saved script arguments, standardizes the input features to the same conventions used during training, and emits per‑record wind predictions together with range‑awareness diagnostics.

## Methodology
The inference workflow executed inside the SageMaker Processing container follows a deterministic, auditable sequence of stages:
1. **Input staging**. GeoParquet shards mounted under `/opt/ml/processing/input` are consolidated into a single DataFrame so that all subsequent operations see a consistent schema. This step also validates that the processing job received data and fails early if the mount point is missing.
2. **Model artefact retrieval**. The helper downloads the `model.tar.gz` bundle referenced by `--model-s3-uri`, extracts it in a scratch directory, and loads the Torch checkpoint together with the persisted `script_args.json`. The checkpoint must embed `normalization_params`, while the script arguments provide feature-engineering and range metadata.
3. **Configuration reconstruction**. Using the model configuration referenced in the saved arguments—either from `/opt/ml/code` or from the payload stored alongside the weights—the routine rebuilds the station catalogue, aggregation strategy, and optional feature switches (`use_mad`, `use_velocity_median`).
4. **Schema harmonisation**. `ensure_standard_columns` enforces the naming conventions expected by the network by cloning or renaming raw observations into canonical fields (e.g. `station_pwr_0`, `station_dist`). Missing mandatory inputs trigger explicit errors so that unexpected upstream changes are surfaced immediately.
5. **Feature engineering**. `engineer_features` recomputes every derived attribute used during training: maximum MAD power, trigonometric encodings of station bearings, canonical distance columns, and optional median radial velocities. The function returns the full feature list that will be passed to the network.
6. **Normalization**. `normalize_features` applies the stored centering and scaling factors, including station-specific conditional mappings when present. Any fallback applied by the conditional normalizer is logged so that analysts can diagnose schema mismatches.
7. **Forward propagation**. The MLP defined in the training library is instantiated with the original topology (hidden layers, units, dropout) and receives the normalized tensor. The forward pass yields the regression head (speed, cosine, sine) and the range-classifier logits, which are converted into probabilities.
8. **Deterministic post-processing**. Wind-direction components are re-normalized to unit vectors and transformed into degrees. Range probabilities are mapped to human-readable labels, the “in-range” probability is exposed explicitly, and confidence scores are computed. A deterministic `pred_speed_range_label` derived from the predicted speed guards the classifier outputs, while proximity and confidence flags highlight near-boundary decisions.
9. **Output materialisation**. The script rewrites the truth columns as `wind_speed` and `wind_dir`, attaches all prediction fields, and persists the table in the requested format (Parquet by default). A companion `inference_metadata.json` captures the model URI, the input record count, the feature columns, and the effective range configuration to aid reproducibility.
10. **Diagnostics orchestration**. Optional post-processing with `compute_inference_metrics.sh` downloads the newly produced predictions, rebuilds the Dockerized analytics image, and executes `compute_inference_metrics.py`, which stratifies regression and classification metrics globally, by maintenance intervals, by user-defined groups, and by wind-speed bins before emitting Markdown reports and CSV summaries.

## Inputs and configuration
- Trained model artifacts placed under the model directory inside the container or mounted path:
  - `model.pth`: serialized network weights; may be a bare state dict or a dictionary with `model_state_dict` and metadata. The checkpoint must embed the `normalization_params` payload produced at training time because the inference script hydrates the scaling statistics from this object rather than from an external JSON.
  - `script_args.json`: exact configuration used for training (stations, schema, targets, range bounds, normalization mode, and other hyperparameters). This file is used to rebuild feature engineering and range settings at inference time.
- GeoParquet input with the station features declared in the model JSON (the same column naming rules from training apply).
- Range configuration derived from `script_args.json`:
  - `range_min`, `range_max`: valid wind‑speed band for range‑aware processing.
  - `range_margin`: boundary margin (m/s) to flag near‑boundary predictions.
  - `range_flag_threshold`: class‑probability threshold to mark a range decision as “confident”.

## Outputs
For each input record, the inference pipeline returns wind predictions and range‑awareness diagnostics. Column names follow the conventions used during training and downstream analysis:
- `pred_wind_speed`: predicted wind speed (m/s).
- `pred_cos_wind_dir`, `pred_sin_wind_dir`: predicted cosine/sine of wind direction; `pred_wind_direction` reconstructs the angle in degrees via `atan2`.
- Range classification probabilities: one column per class, named `prob_range_<label>` (labels taken from `range_class_labels` in `script_args.json`).
- `pred_range_label`: predicted range class (`below`, `in`, or `above` by default), with `pred_range_confidence` equal to the top class probability. A convenience `prob_range_in` is provided for the “in‑range” class index.
- `pred_speed_range_label`: deterministic range label derived from the continuous wind‑speed prediction and the configured bounds; downstream consistency checks compare this column against `pred_range_label`.
- Boundary proximity flags computed from the configured margin: `range_near_lower_margin`, `range_near_upper_margin`, and `range_near_any_margin`.
- `range_flag` and `range_flag_confident`: categorical and boolean indicators of a confident range decision vs `uncertain`, using `range_flag_threshold`.
- `range_prediction_consistent`: boolean consistency between the classifier’s label and the speed‑based label relative to the configured band.

Metadata is also written to `inference_metadata.json` alongside the tabular output, including the model artifact URI (when available), the ingested row count (`input_rows`), feature columns, and the effective range configuration used (`range_min`, `range_max`, `range_margin`, `range_flag_threshold`, and class labels).

## Notes
- The inference script reloads the same normalization mode and statistics used during training; do not recompute normalization on inference data.
- If `script_args.json` specifies `hidden_layers=0`, the network backbone is an identity; predictions are still valid as the learned heads operate on the engineered features.
- To ensure schema compatibility, use the same model JSON (schema/stations) that was used to train the deployed model; feature engineering applies the same renaming and encoding rules.

## Maintenance-aware inference metrics
`compute_inference_metrics.sh` orchestrates the post-processing of inference outputs. The helper downloads the predictions parquet (and optional metadata JSON) from S3, rebuilds the metrics Docker image on demand, and runs `compute_inference_metrics.py` inside the container so that pandas, pyarrow, and the scientific Python stack remain isolated from the host environment. The generated artefacts are placed under `artifacts_root/<pipeline>/inference_metrics` alongside the inference run identifier.

`compute_inference_metrics.py` continues to publish the aggregated tables in `inference_metrics_report.md` and the flattened CSV (`inference_metrics.csv`). The Markdown report now includes an additional section titled “Maintenance interval analysis” that scans every column containing `maintenance_interval` (for example `site1_maintenance_interval_id` or `site2_maintenance_interval_id`) and computes per-interval diagnostics together with the global aggregates. For each interval, the report enumerates the sample support, RMSE, MAE, the angular mean absolute error, and the macro-F1 when range classification labels are available. Three tables are produced per maintenance column: one covering the full population, a second restricted to samples whose true speed falls inside the operational range, and a third that keeps only the in-range observations whose range classification agrees with the speed-based label. Intervals whose RMSE or angular MAE exceeds the relevant baseline by more than fifteen per cent, or whose macro-F1 drops by more than 0.15, are highlighted in narrative comments urging maintainers to revisit the calibration chronology documented in `docs/aggregation/attach_station_maintenance_table.md`.

All interval metrics are also exported to `inference_metrics_by_interval.csv` so that analysts can ingest the maintenance-aware diagnostics into exploratory notebooks or monitoring dashboards. The CSV mirrors the report structure, prefixing the in-range columns with `in_range_` and the matched subset with `matched_`, while preserving the existing (all-sample) fields for backwards compatibility. Rows with `NULL` in the interval column correspond to predictions where the pivot-and-join pipeline could not associate a maintenance window; the report explicitly reminds readers to benchmark those rows against the global values rather than interpreting them as anomalies. Short intervals covering fewer than five per cent of the samples or holding fewer than twenty-four records are excluded from the automatic degradation alerts to avoid spurious triggers caused by sampling noise.

## Wind-bin stratification
To mirror the regression diagnostics produced during training, `compute_inference_metrics.py` now stratifies every inference run by the `wind_bin` column whenever it is present in the predictions parquet. The resulting tables—`inference_metrics_by_wind_bin.csv`, `inference_metrics_in_range_by_wind_bin.csv`, and `inference_metrics_matched_by_wind_bin.csv`—reuse the layout of the training artefacts (`metrics_fold-1_by_wind_bin.csv`) so that downstream notebooks can compare training and inference behaviour without additional reshaping. The Markdown report also gains a dedicated “Wind bin analysis” section that lists RMSE, MAE, angular errors, and macro-F1 per bin for the three canonical subsets (all samples, in-range records, and in-range points whose range-classification matches the speed-derived label). Each table annotates the relative deviation against the global baseline and issues a narrative alert whenever a bin exceeds the 15% degradation threshold or erodes macro-F1 by more than 0.15. Bins labelled as `NULL` arise when the predictions lack a wind-bin assignment and are meant to be interpreted in the light of the global aggregates.
